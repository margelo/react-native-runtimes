Background work runs JS on a named threaded runtime without mounting any UI.
Register a `runtimeFunction` and invoke it with `schedule` when a runtime
should fetch, hydrate, decode, or update shared state before a screen opens.
Scheduled functions do not return values to the caller; they publish durable
output through shared state, storage, or native modules.

The same mechanism can also run heavier business logic away from the main JS
runtime. See [Background thread architecture](/docs/threaded-runtime/business-logic-executor)
for a crypto-style job queue example.

## Register a runtime function

Register inside code loaded by the threaded bundle — typically a
[per-runtime bootstrap file](/docs/getting-started/metro-setup#per-runtime-bootstrap-files).
Give it a stable id with `runtimeFunction.named(...)` so native callers can
reference it:

```tsx
import { runtimeFunction } from '@react-native-runtimes/core';
import { messagesStore } from './messagesStore';

export const hydrateConversation = runtimeFunction.named(
  'messages.hydrateConversation',
  async ({
    conversationId,
    limit,
  }: {
    conversationId: string;
    limit: number;
  }) => {
    const messages = await loadMessages(conversationId, limit);

    await messagesStore
      .path<Message[]>(['conversations', conversationId])
      .set(messages, true);
  },
);
```

## Schedule from JS

```tsx
import { schedule } from '@react-native-runtimes/core';
import { hydrateConversation } from './hydrateConversation';

await schedule(hydrateConversation).on('conversation-worker-runtime')({
  conversationId: 'release-room',
  limit: 50,
});
```

Native starts or reuses the named runtime. If the runtime is still starting,
the function is queued and flushed after startup.

<Callout type="warn" title="The promise resolves on dispatch, not completion">
  `schedule` resolves when native **accepts** the work, not when the async
  function body finishes. Use shared state to observe progress, or use `call`
  for request/response work.
</Callout>

## Await results with `call`

For request/response work, use `call`, which is awaitable and returns the
function result:

```tsx
import { call, runtimeFunction } from '@react-native-runtimes/core';

export const readConversation = runtimeFunction(
  async ({ conversationId }) => {
    const messages = messagesStore.path<Message[]>([
      'conversations',
      conversationId,
    ]);

    await messages.hydrate();
    return messages.get();
  },
);

const messages = await call(readConversation).on(
  'conversation-worker-runtime',
)({ conversationId: 'inbox' });
```

The Metro wrapper assigns the exported function a stable id and rewrites the
`call(...).on(...)` / `schedule(...).on(...)` calls to dispatch them to the
requested runtime. See
[Scheduling functions on another runtime](/docs/threaded-runtime/scheduling-functions)
for the full API contract and lookup model.

## Native schedule

When JS isn't a convenient caller — for example from a foreground service or
a notification handler — schedule from native code instead. Native callers
reference the function by its id and pass JSON-stringified arguments (a JSON
array of the function's arguments).

<Tabs items={['Android (Kotlin)', 'iOS (Swift)', 'Android (C++)', 'Apple (C++ / Obj-C++)']}>

<Tab value="Android (Kotlin)">

```kotlin
ThreadedRuntime.schedule(
  context = applicationContext,
  runtimeName = "conversation-worker-runtime",
  functionId = "messages.hydrateConversation",
  argsJson = """[{"conversationId":"release-room","limit":50}]""",
)
```

</Tab>
<Tab value="iOS (Swift)">

```swift
ThreadedRuntime.schedule(
  withRuntimeName: "conversation-worker-runtime",

)
```

</Tab>

## Typical flow

1. Prewarm the runtime while the user is still on the previous screen.
2. Schedule a runtime function to hydrate data on that runtime.
3. Store durable output in shared state or native storage.
4. Open a `ThreadedScreen` using the same runtime name.
5. The screen reads the already-warmed data from the shared store.

<Callout type="info" title="Why this layered approach helps">
  By the time the user navigates, the runtime is alive, the data is loaded,
  and the screen mounts against a populated store. The transition feels
  instant.
</Callout>
