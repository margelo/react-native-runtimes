## Core: JS API

### Components

`OnRuntime` — declarative mount. Accepts exactly one direct top-level component as a child. Metro rewrites that child into a `threadedComponent` registration.

```tsx
<OnRuntime name="messages-runtime">
  <MessageList conversationId="release-room" />
</OnRuntime>
```

Props on the child are serialized as JSON and forwarded to the threaded surface. `OnRuntime` itself takes:

- `name: string` — runtime name (required).
- Any other props are passed through to the underlying surface; valid surface props below.

`Threaded` — explicit mount when you have a `threadedComponent`-registered component and want to control surface props directly.

```tsx
<Threaded
  component={MessageList}
  props={{ conversationId, initialIndex }}
  runtimeName="messages-runtime"
  surfaceKey="messages-release-room"
/>
```

`ThreadedScreen` — full-flex screen variant with built-in preload. Use for whole routes.

```tsx
<ThreadedScreen
  component={ConversationScreen}
  props={{ conversationId }}
  runtimeName={`conversation-${conversationId}-runtime`}
  destroyOnUnmount      // optional — destroy the runtime when the screen unmounts
  testID="conversation-threaded-screen"
/>
```

`ThreadedReactSurface` — lower-level component that takes a component **name** (string) rather than a registered component reference. Useful when the name is computed at runtime.

```tsx
<ThreadedReactSurface
  componentName="ExpensivePanel"
  initialProps={{ mode: 'compare' }}
  runtimeName="analytics-runtime"
  style={{ flex: 1 }}
  surfaceKey="analytics-panel"
/>
```

Changing `componentName`, `initialProps`, `runtimeName`, or `surfaceKey` restarts the native surface.

### Component registration

`threadedComponent<Props>(name, Component)` — registers a component under a stable name. The name is what the threaded surface looks up.

```tsx
export const ConversationScreen = threadedComponent<ConversationScreenProps>(
  'ConversationScreen',
  function ConversationScreen(props) { return <ConversationRoute {...props} />; },
);
```

`registerThreadedComponent(name, Component)` — register at module load time without a component wrapper. Use when you generate registrations yourself.

`registerLazyThreadedComponent(name, () => Component)` — same, but the import is deferred until the component name is actually mounted. The Metro-generated entry uses this form to avoid eagerly loading every threaded component on secondary runtime startup.

### Runtime functions

`runtimeFunction(fn)` — wrap an exported function so it can be called from another runtime. Metro assigns it a stable id derived from `file path + export name`.

```tsx
export const fibonacci = runtimeFunction((n: number) => /* ... */);
```

`runtimeFunction.named(id, fn)` — explicit stable id. Use this when the file path should not be part of your function's "public" id.

`runtimeFunction.withId(id, fn)` — used by the Metro transform for the directive-shortcut output. You normally won't write this by hand.

`call(fn).on(runtimeName)(...args)` — schedule a `runtimeFunction` on a named runtime, return a Promise. Metro rewrites this to a direct `fn.runOn(runtimeName, ...args)` call.

```tsx
const result = await call(fibonacci).on('fibonacci-worker')(38);
```

`fn.runOn(runtimeName, ...args)` — the underlying call form. Generated by Metro but also directly usable.

`usingRuntime(name).run(() => fn(args))` — legacy callback form. The callback must contain exactly one call to one exported `runtimeFunction`. Still supported.

**Function directives** — Metro-only shortcut. The first statement of a top-level function body, written as a string literal naming the target runtime:

```tsx
async function refreshCache(key: string) {
  'background';
  // body runs on the 'background' runtime
}
```

The directive name is the runtime name. `'background'` and `'main'` are commonly used by convention, but any string is valid as long as the runtime exists.

### Headless tasks

`registerThreadedHeadlessTask<Payload>(name, handler)` — register a task that runs on whichever runtime calls it. The handler receives `{ payload, runtimeName }`.

```tsx
registerThreadedHeadlessTask<{ conversationId: string; limit: number }>(
  'hydrateConversation',
  async ({ payload, runtimeName }) => { /* ... */ },
);
```

`ThreadedRuntime.runHeadlessTask(name, { runtimeName, payload })` — dispatch the task. **Resolves when native accepts the dispatch, not when the handler finishes.**

```tsx
await ThreadedRuntime.runHeadlessTask('hydrateConversation', {
  runtimeName: 'conversation-worker-runtime',
  payload: { conversationId, limit: 50 },
});
```

### ThreadedRuntime lifecycle

- `ThreadedRuntime.prewarm(name, options?)` — create and start a named runtime; load the bundle; do not mount a surface. `options` accepts `{ kind?: string, useMainNativeModules?: boolean }`. Returns a Promise that resolves when the runtime is ready.
- `ThreadedRuntime.preload(name)` — alias for `prewarm`.
- `ThreadedRuntime.destroy(name)` — tear down the named runtime, free its bundle/modules/subscriptions.
- `ThreadedRuntime.destroyAll()` — tear down every named runtime currently alive.
- `ThreadedRuntime.getRuntimeNames()` — `Promise<string[]>` of currently active runtimes.
- `ThreadedRuntime.runHeadlessTask(name, options)` — see above.

## Core: Metro wrapper

```js
const { withThreadedRuntime } = require('@react-native-runtimes/core/metro');

module.exports = withThreadedRuntime(
  mergeConfig(getDefaultConfig(__dirname), config),
  {
    roots: ['App.tsx', 'src'],     // scan paths for OnRuntime / threadedComponent / runtimeFunction / function directives
    generatedDir: '.threaded-runtime',
    generatedEntry: 'entry.js',
  },
);
```

What it does:

- Walks `roots` for:
  - `OnRuntime` children → emits `threadedComponent(name, Component)` registrations + exports the child as a const.
  - Top-level `export const X = runtimeFunction(...)` → emits `registerRuntimeFunction(id, () => require(file).X)` in the generated entry.
  - Top-level function declarations whose body starts with a string-literal directive → rewrites to `export const X_ = runtimeFunction.withId(...)` plus a `const X = call(X_).on('directive')` local alias.
  - `call(fn).on(name)(...args)` → rewrites to `fn.runOn(name, ...args)` for efficiency.
- Writes `<generatedDir>/<generatedEntry>` containing all registrations + `AppRegistry.registerComponent('ThreadedRuntimeHost', () => ThreadedRuntimeHost)`.
- Adds `<generatedDir>` to Metro's `watchFolders`.
- Discovers root-level `index.<runtime>.ts` files and emits static conditional requires for them in the generated entry, gated on `global.__THREADED_RUNTIME_ENV__.kind` / `.runtimeName`.

Generator rules (will fail the build if violated):
- Component names must be unique.
- Threaded components must be named exports.
- The generated output is deterministic for the same source.

## Core: Native dispatch

Every JS-side `ThreadedRuntime` method has a native counterpart. Use these when native code (a background service, a native module, a Swift/Kotlin entry point) needs to drive the runtime before JS is on the stack.

### Kotlin (Android)

```kotlin
import com.nativecompose.threadedruntime.ThreadedRuntime

// Lifecycle
ThreadedRuntime.prewarmRuntime(applicationContext, "name")
ThreadedRuntime.prewarmRuntimeWithOptions(applicationContext, "name", kind, useMainNativeModules)
ThreadedRuntime.prewarmBusinessRuntime(applicationContext, "business-runtime")
ThreadedRuntime.preloadRuntime(applicationContext, "name")
ThreadedRuntime.destroyRuntime(applicationContext, "name")
ThreadedRuntime.destroyAllRuntimes(applicationContext)
ThreadedRuntime.getRuntimeNames(applicationContext) // List<String>

// Headless dispatch (queued if runtime is still starting)
ThreadedRuntime.dispatchHeadlessTask(
  context = applicationContext,
  runtimeName = "conversation-worker-runtime",
  taskName = "hydrateConversation",
  payloadJson = """{"conversationId":"inbox","limit":50}""",
)

// Native-module package providers
ThreadedRuntime.setExtraReactPackagesProvider { listOf(/* packages threaded runtimes need */) }
ThreadedRuntime.setMainReactPackagesProvider { PackageList(this).packages } // for business runtimes
```

### Swift (iOS)

```swift
import NativeComposeThreadedRuntime

// Required once, before the first surface:
ThreadedRuntime.configure(
  withReactNativeDelegate: delegate,
  launchOptions: launchOptions
)

// Lifecycle
ThreadedRuntime.prewarmRuntime("name")
ThreadedRuntime.prewarmBusinessRuntime("business-runtime")
ThreadedRuntime.destroyRuntime("name")
ThreadedRuntime.destroyAllRuntimes()

// Headless dispatch
ThreadedRuntime.dispatchHeadlessTask(
  withRuntimeName: "conversation-worker-runtime",
  taskName: "hydrateConversation",
  payloadJson: #"{"conversationId":"inbox","limit":50}"#
)
```

### C++ (both platforms)

```cpp
#include <nativecompose/threadedruntime/ThreadedRuntimeDispatcher.h>

// Android requires JNIEnv* and the Application context jobject.
nativecompose::threadedruntime::prewarmRuntime(/* args */);
nativecompose::threadedruntime::dispatchHeadlessTask(
  /* env, context (Android only), */
  "conversation-worker-runtime",
  "hydrateConversation",
  R"({"conversationId":"inbox","limit":50})"
);
```

Queueing behavior: if the named runtime is still starting when a headless dispatch lands, native enqueues it and flushes the queue once startup completes. If the runtime has not been created at all, native creates and starts it first, then dispatches.

## State: createSharedStore

```ts
import { createSharedStore } from '@react-native-runtimes/state';

const store = createSharedStore<State, Action?>({
  name: 'unique-store-name',
  initialState: { /* JSON-serializable shape */ },

  // Optional: paths to hydrate eagerly during store creation. Use for known hot paths.
  subtrees: ['catalog', 'pokemonItems'],

  // Optional: reducer style. Reducers run in the JS runtime that calls dispatch.
  reducer(state, action) { /* ... */ },

  // Optional: slice reducers, one per top-level subtree.
  slices: {
    business: (state, action) => /* ... */,
  },

  // Optional: native persistence.
  persist: {
    key: 'unique-persistence-key',
    subtrees: ['counter'],      // which paths should be persisted/restored
    version: 1,                 // optional schema version
  },
});

// Top-level API (legacy but supported):
store.dispatch(action);
store.useStore(selector);

// Recommended API:
const handle = store.path<T>(pathStringOrArray);
```

Hydration uses a native `getOrInit` that atomically initializes the persisted JSON if missing — concurrent runtimes will not both observe an empty store and race to write defaults.

## State: path handles

`store.path<T>(path)` — path is a dot-string (`'conversations.release-room'`) or array (`['conversations', 'release-room']`). Both become the same native key.

```ts
const messages = chatStore.path<Message[]>(['conversations', conversationId]);

// Async — wait for the native commit:
await messages.set(value, broadcast?);      // commit; broadcast=true by default
await messages.update(prev => next);        // atomic read-modify-write
await messages.hydrate();                   // ensure native value is loaded
await messages.clear();                     // remove this path

// Synchronous — these return immediately. Do NOT await:
const value = messages.get();               // current snapshot (no Promise)
const value = messages.use();               // React hook (subscribes; sync render value)
const count = messages.use(v => v?.length ?? 0); // with selector
const rev = messages.getRevision();         // native revision counter
```

The sync methods read the in-process C++ snapshot, which is updated on every commit. They don't return Promises — awaiting `path.get()` just unwraps the value (a no-op) and hides the fact that a future API change to make it async would not surface as a type error at the call site.

Path subscribers are invalidated for related paths in both directions: subscribers on `conversations` see changes to `conversations.release-room`, and subscribers on `conversations.release-room` see changes to `conversations`.

## State: persistence

`persist.subtrees` lists paths to eagerly restore during store creation. Dynamic paths not listed there still hydrate lazily when `store.path(...).use()` first subscribes, or when you call `path.hydrate()` explicitly.

Persisted state is stored as native JSON files keyed by `persist.key + subtree path`. If `version` is bumped and the on-disk version differs, the old payload is discarded and `initialState` is used (no built-in migrations — write your own with a one-shot reducer if needed).

## Globals available inside a threaded runtime

Inside any non-main runtime:

- `global.__THREADED_RUNTIME_ENV__` — `{ kind: string, runtimeName: string }`. `kind` is set by `prewarmRuntimeWithOptions(..., kind, ...)` or `prewarmBusinessRuntime` (`"business-runtime"` by default); `runtimeName` is always the runtime's name.
- `global._is_it_a_list_env === true` — a legacy alias used by some examples. Either of `__THREADED_RUNTIME_ENV__` or `_is_it_a_list_env` is a reliable "I'm in a threaded runtime" check.

Inside the main runtime, both are `undefined`.

Use these to gate runtime-specific startup code in `index.js` and in root-level `index.<runtime>.ts` files.
